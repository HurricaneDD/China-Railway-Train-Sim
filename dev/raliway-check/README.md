# 线路人工检查（dev/raliway-check）

这是一个独立的线路拓扑人工检查页，用于分省核对当前运行数据中的正线断点、被过滤的端点连接和桥隧/层级过渡。它只读取 `data/` 下的正式分省 GeoJSON，不修改原始数据、不生成存档，也不参与驾驶。

## 打开方式

开发环境：

```bash
npm run dev
# http://localhost:8062/dev/raliway-check/
# 外部访问示例：http://fangxx.fun:8062/dev/raliway-check/
```

末尾的 `/` 不能省略。开发服务器会对 `/dev/raliway-check`（无尾斜杠）返回 302 跳转到带斜杠地址；若使用旧进程或把该路径交给普通静态服务器的 SPA 回退，可能显示主应用首页。主应用的“设置 → 数据来源与许可”也提供入口。

生产构建会把页面输出到 `dist/dev/raliway-check/index.html`。该页面不加载 Cesium；`vite.config.ts` 中的 `railway-check-html` 插件会移除 Cesium 插件注入到该嵌套页面的静态标签，避免相对路径 404。

## 数据与计算

- 省份列表来自 `data/provinces_index.json`，线路来自对应的 `data/geojson/<adcode>-<省份>.geojson`。
- 页面通过注入 `RailwayRepository` 的 `JsonFetcher` 读取 `../../data/`，适配开发服务器和 GitHub Pages 的嵌套路径。
- 拓扑规则与驾驶会话共用 `src/data/railway.ts`：原始 part 独立、2 m 端点节点、0.25 m 连接容差、0.25 m/35° 桥隧过渡限制。
- 共享原始端点（间隙 < 0.01 m）存在桥隧或 `layer` 标签差异时，只要转角不超过 35°，仍按几何连续性保留为可行驶候选，并标记为“不确定”。这是 2026-11-02 修复正线误断的核心规则。
- 桥隧识别仅依据原始属性：`bridge === 'T'` 为桥，`tunnel === 'T'` 为隧；`'F'`、缺失或其他值都不算。它不是结构检测，也不使用 DEM 或几何形态分类。

## 断点分类

- **存在被过滤连接**：到达节点没有有效出边，但存在被当前规则拒绝的非掉头候选。最值得优先检查。
- **邻近线路未接入**：没有候选，但 100 m 内存在其它线路区段。可能是省界、真实断头、站场股道或 OSM 缺口。
- **孤立端点**：100 m 内没有其它线路。可能是真实支线终点、站场尽端或更大的数据缺口。
- 只有“接近掉头”被拒绝的方向不会被视为断点，因为倒车回头由驾驶操作处理。
- 弱连通分量是按有效区段连接计算的并查集结果，忽略方向和区段内细分，不是实际可达性。

## 人工检查流程

1. 选择省份，加载当前原始数据。
2. 先看“重点”列表和红色断点；选中后查看来路、候选、间隙、角度、桥隧/层级标签。
3. 必要时勾选“加载相邻省份”，复核省界断点；已加载数据在本次会话内保留。
4. 开启“显示被过滤连接”查看被拒绝的几何连接；导出本省 JSON 作为修复线索。
5. 修复原始数据后重新加载，确认断点消失且未引入新的多出口误连。不要用本工具自动改数据。

## 验证

```bash
npm test
npm run build
```

`tests/railway-check.test.ts` 覆盖共享端点桥隧/层级过渡、0.55 m 间隙断点识别和孤立端点分类。页面已在开发服务器和无 Cesium 的生产构建中实际加载；完整浏览器驾驶验收仍以主应用为准。
